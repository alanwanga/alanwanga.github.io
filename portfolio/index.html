Technical Work

  • Perception from pixels: Gemini Robotics-ER points at objects in simulated RGB-D camera frames; points are back-projected with depth and tracked via a Kalman filter with Hungarian association (recall 0.80–0.82 at precision 0.95–0.96).
  • Robustness: across three seeded scene layouts, VLM-grounded planning succeeded on 29 of 30 runs; with walking bystanders, live Gemini runs succeeded 18 of 18 with 0 violations; under random mid-cruise gusts, 120 runs had 0 geofence, no-fly, or separation violations.

  • (Original PoC) Text descriptions generate custom 3D test scenes; commands, reasoning, actions, and feedback are logged as episodes for a reinforcement-learning dataset.

ros_gz: Clean Shutdown of the Gazebo Simulation Interfaces

Gazebo
C++ ROS 2 rclcpp Concurrency

Problem

The GzServer ROS 2 component initialized its simulation interfaces in a detached thread that could wait several seconds for Gazebo. Shutting the component down during that window (e.g. Ctrl+C right after startup) destroyed the interfaces while the thread was still running, so the node and the rclcpp context stayed alive until exit and the thread could touch freed memory.

Fix

Joined the thread in the destructor instead of detaching it, and added a stop flag so the waits for Gazebo end early on shutdown, plus a regression test that fails without the fix. With Ctrl+C 1–2 s after startup, the rclcpp context's use count at exit dropped from 3 to 1; normal startup is unchanged.

Why It Matters

Composable ROS 2 nodes are loaded and unloaded inside long-running containers; a thread that outlives its component leaks the context and can touch freed memory in a process that keeps running.

gz-physics MuJoCo Plugin: Nested-Model Removal

Gazebo
C++ MuJoCo Physics Simulation Testing

Problem

The MuJoCo physics plugin advertised entity removal, but removing a nested model by index or by name was a TODO stub that always returned false, so the call silently did nothing. Existing tests skipped this path for MuJoCo.

Fix

Implemented both the same way as top-level model removal: look up the direct child and reuse the existing removal path, which already removes grandchildren. Missing names, out-of-range indices, and already-removed models return false. A new cross-engine test fails without the fix.

Why It Matters

A silent no-op is worse than an error in simulation: the scene looks updated but still contains the model, so the physics no longer matches what the caller believes.

gz-physics MuJoCo Plugin: Reject Cross-World Constraints

Gazebo
C++ MuJoCo Physics Simulation Reliability

Problem

Attaching a fixed joint or setting a mimic constraint accepted an endpoint from a different world. The plugin wrote that world's body or joint name into this world's MuJoCo model, so the next recompile failed and the following simulation step segfaulted.

Fix

Check that both endpoints belong to the same world before changing anything. A cross-world call now logs an error and is rejected, leaving both worlds unchanged. New tests make a cross-world call and then step both worlds; without the fix they segfault.

Why It Matters

Running several worlds in one process (e.g. parallel simulations) should fail with a clear error on invalid input, not crash the whole process.

Open-RMF rmf_traffic: Per-Lane Speed Limits

Open-RMF
C++ Trajectory Planning Multi-Robot Traffic Testing

Problem

When collinear lanes were merged into one traversal, the whole stretch was capped at the lowest speed limit; on longer corridors the planner instead chained single-lane traversals that each start and end at rest. With three 5 m lanes limited to 1.0 / 0.3 / 1.0 m/s, the robot stopped twice and took 31.3 s.

Fix

Kept each lane's own limit and built the motion profile with a forward (acceleration) and backward (deceleration) pass, so the robot slows down before the slow lane and speeds up after it without stopping: 29.6 s with no stops. Uniform-limit traversals are unchanged and there are no public API changes; a new test scenario fails on the main branch.

Why It Matters

Fleet traffic schedules are only as good as the trajectories they are built from. At Wing I debugged cross-operator 4D deconfliction incidents on call (InterUSS / ASTM F3548); rmf_traffic's traffic schedule and conflict checks are the same class of problem.

MuJoCo: Camera Intrinsics Utility

MuJoCo
C++ MuJoCo Rendering Perception

Problem

Projecting 3D points into rendered images, or back-projecting depth, needs the camera's pixel intrinsic matrix, and callers had to re-derive it for each camera type.

Fix

Implemented a utility that returns the pixel intrinsic matrix for a given viewport size, consistent with what the renderer draws.

Why It Matters

Perception pipelines built on MuJoCo rendering, such as TAnGY's depth back-projection, need intrinsics that match the renderer exactly.
